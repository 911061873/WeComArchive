# 第一版重构设计

以 [项目规划](项目规划.md) 为唯一需求依据，公开 API 不兼容旧开发版。

## 现状检查与取舍

旧版本采用线程 worker、持久化解析/下载/消费任务，成功解密后不保留密文；
普通拉取异常终止采集，包含重启唤醒等待密钥、附件下载恢复等流程。
这些行为与新规划冲突，已移除对应 worker、repository、下载路径及任务状态模型。
旧补解密脚本、旧同步消费者入口与相关测试也由新流程替代。

保留原有 SDK 的调用方式、RSA 随机密钥解密方式、按版本选密钥（0 为回退）、
SQLAlchemy 事务存储和 Pydantic 校验思路。补充所有密文留存、类型表、独立文本规则、
进程内异步队列及 Alembic 迁移。没有加入客户关系、回调、管理页面、外部队列、任务恢复。

## 目录与边界

| 模块 | 职责 |
| --- | --- |
| `config.py` | Pydantic 配置校验，无隐式环境变量 |
| `models.py` | 加密输入与消费消息 |
| `sdk.py` | pyweworkfinance 适配、密钥与同步客户端边界 |
| `parser.py` | 类型内容提取，不涉及网络和数据库 |
| `storage.py` | 单批准备、去重、消息与游标原子提交 |
| `db/` | ORM 表、连接与启动版本检查 |
| `rules.py` | 文本包含/正则匹配，启动时编译正则 |
| `service.py` | 专用 SDK/DB 线程、异步轮询分发、背压与生命周期 |
| `migrations/` / `cli.py` | 随包发布的 Alembic 固定版本脚本与显式升级入口 |

SDK 和数据库共用一个专用线程，避免原生 SDK 并发安全假设、避免阻塞事件循环；
只在内存中保留一批处理结果，提交后才交给异步队列。首版选择串行解密，以简单可验证的事务边界为先。
公共 `run()` 只能调用一次，规则和密钥只允许启动前注册。

## 表结构

- `archive_progress`：单行 id=1，保存最大已提交 seq，空表等价于游标 0。
- `archive_encrypted`：msgid 主键、seq 索引、完整密文 JSON、解密错误、归档时间。
- `archive_decrypted`：以 msgid 外键关联密文，保存 msgtype、msgtime、完整明文 JSON 和类型解析错误。
- `archive_type_<类型>`：每种类型独立一表，msgid 外键关联明文，payload 保存对应类型完整对象。
  text 额外提取 content；媒体类型额外提取 sdkfileid、filename、filesize、md5sum。
- `alembic_version`：数据库结构版本；不包含消费任务表或附件下载表。

表使用可移植的 SQLAlchemy JSON、BigInteger、Text；不用数据库专有 upsert，
依赖单采集实例与主键约束去重。消息 ID 在 MySQL 上明确区分大小写。

## 类型清单与支持深度

旧解析器处理 10 种附件类型：image、voice、video、emotion、file、mixed、
meeting_voice_call、voip_doc_share、note、chatrecord。
其余 21 种仅标记为不含附件，没有独立字段表。

新版本为以下 31 种建立类型表：

```text
text image voice video emotion file mixed meeting_voice_call voip_doc_share
chatrecord revoke agree disagree card location link weapp collect redpacket
meeting meeting_notification docmsg markdown news calendar external_redpacket
sphfeed voiptext qydiskfile solitaire note
```

text 校验字符串正文；7 种直接媒体类型校验媒体 ID 和可选大小/文件名/摘要并提取列；
mixed、chatrecord、note 校验子项数组，保留完整嵌套数据，不递归下载或拆成附件任务。
note 的类型字段是 `info`。其余类型提取同名对象，完整保存其字段，不声称对每个业务字段做严格校验。
未知类型、缺少类型字段、非法已支持字段都不会丢失基础明文。

## 默认值与可靠性边界

轮询 1 秒、每批 1000、SDK 超时 5 秒、消费窗口 300 秒、队列 1000、工作任务 4、关闭等待 30 秒。
时间窗口仅影响消费，不影响存档；同一消息多规则命中分别执行，副作用由业务自行管理。
发送者过滤未实现，未来可扩展规则类型，而不是在第一版暴露无效配置字段。

提交和进程内分发之间存在不可消除的退出窗口。此设计不恢复已经存档的消费；
不添加 outbox、不补偿失败、不重放历史。整个实例只有一个拉取提交者；不支持多进程争用一个游标。
