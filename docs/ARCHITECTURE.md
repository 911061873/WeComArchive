# 系统架构

## 当前状态

客户联系资料目录的首版公共 API、同步流程、数据模型和数据库初始化已经实现。会话存档核心数据流与 API 边界已经确定，部署方式以及企业微信 SDK 集成细节仍待确认。

## 交付形态

- 项目以可安装的 Python 包交付。
- 项目使用 Python 3.10，并使用 uv 管理虚拟环境、依赖声明和锁定文件。
- 安装后通过 `WeComArchive` 类提供会话存档配置、初始化和消息同步能力。
- 客户、客户群及群成员资料同步属于独立的 `CustomerContactDirectory` 公共组件，不作为 `WeComArchive` 的方法。
- 首版不提供命令行工具；内部实现不作为公共 API。
- “开箱即用”需要通过默认配置、清晰的错误提示和最少的初始化步骤实现，但不得以不安全的默认值处理密钥或真实会话数据。

### `WeComArchive` 的初步职责

- 初始化时接收并校验必填的企业微信会话存档凭据。
- 接收可选的数据库配置；未提供时自动使用 SQLite，提供时连接用户指定的受支持数据库。
- 通过企业微信会话存档 SDK 获取、解密会话数据及下载附件，不提供 HTTP 服务，也不创建 httpx 客户端。
- 接收轮询间隔配置。
- 初始化完成后允许用户通过注册方法添加一个或多个消息处理函数。
- `register_handler` 接收可选的稳定名称；未提供时由函数模块名和限定名生成，名称冲突在运行前报配置错误。
- 管理会话存档 SDK、存储和处理管线组件的生命周期。
- 提供阻塞式 `run_forever()`，按照配置间隔长期轮询消息；消息持久化是不可省略的默认行为。
- 提供 `stop()`，用于从程序内请求优雅停止。
- 将内部异常转换为稳定、可理解的公开异常类型。

构造参数的具体类型、默认轮询间隔、停止时的安全处理边界和资源释放细节仍待确定。

### 客户联系资料目录

- 客户联系专属实现统一位于 `wecom_archive.customer_sync` 子包，包括同步外观、REST API 客户端、响应结构、资料模型、仓储、公开数据类型、异常和当前 schema 迁移；后续会话存档实现不放入该子包。
- `wecom_archive` 包根只重新导出 `CustomerContactDirectory` 及其公开数据类型和异常，继续提供简洁稳定的公共导入路径；客户同步内部组件不作为公共 API。
- 以 `CustomerContactDirectory` 作为独立公共组件，统一协调客户、客户群和群成员资料的同步与本地查询。
- 首版只支持企业内部自建应用认证，初始化时接收企业 `corp_id` 和“客户联系 Secret”；第三方服务商授权模式不在首个里程碑范围内。
- 内部按职责拆分客户同步、客户群同步和资料仓储；具体企业微信 API 调用顺序必须在实现前依据官方文档确认。
- 提供异步 `sync_all_once()` 同步全部客户联系资料，并允许通过异步 `sync_customers_once()` 和 `sync_group_chats_once()` 分别触发客户或客户群同步；查询与资源释放接口同样为异步。
- 负责持久化客户、客户群、群成员关系、各自同步检查点和最后同步时间。
- 与会话存档模块共享数据库基础设施，但独立持有客户联系 REST API 所需的凭据、httpx 客户端、可选代理配置、同步状态和错误处理。
- `WeComArchive` 始终保存消息中的原始成员 ID、客户 ID 和群 ID，不在消息归档链路中实时请求客户联系 API。
- 消息处理器或查询层可以通过资料目录按 ID 获取当前客户或群资料；资料暂缺不得阻塞或回滚会话归档，后续同步完成后通过关联查询自然补全。

### 数据库兼容

- 使用 SQLAlchemy 2.x 异步 ORM 隔离数据库方言差异；现有 Alembic 配置负责将数据库初始化到当前 schema。
- 首版目标数据库为 SQLite、MySQL 和 PostgreSQL。
- 未提供数据库配置时自动创建基于 `aiosqlite` 的 SQLite 连接；MySQL 和 PostgreSQL 分别使用 `asyncmy` 与 `asyncpg`，并统一通过 SQLAlchemy ORM 访问。
- 生产环境可以显式配置 MySQL 或 PostgreSQL。
- 当前数据模型、初始化和测试不得依赖某一种数据库专有能力，必要的差异应集中封装。
- 默认 SQLite 的并发限制仍需进一步验证。
- 客户同步由资料目录对成员分组创建有限并发任务；内部 HTTP 客户端只负责顺序遍历单个分组的游标并按页返回数据。每页数据通过单写入锁顺序批量写入，默认 SQLite 不启动并发写事务。
- `CustomerContactDirectory` 首次进入异步上下文或首次执行公开异步方法时，通过异步连接运行现有 Alembic 初始化流程并达到当前 schema；初始化失败则不执行资料同步。默认 SQLite 与显式数据库 URL 使用相同路径。
- 项目处于开发阶段，schema 尚未稳定；现阶段不承诺旧开发数据库到新 schema 的升级兼容性，也不把迁移脚本设计和历史版本迁移测试列为近期工作。发生不兼容变更时允许重建开发数据库。
- 进入稳定发布或需要保留真实环境数据前，必须重新确定版本化迁移、回滚、备份和发布流程。
- 初始化时可以配置 `data_dir`；未配置时使用操作系统规范的用户数据目录。
- 默认 SQLite 数据库文件和本地附件根目录均位于 `data_dir` 下，使用相互独立的子路径。

### 网络访问与代理

- `CustomerContactDirectory` 调用客户和客户群 REST API 时只使用 `httpx.AsyncClient`。
- `CustomerContactDirectory` 可以接收可选的 HTTP 代理配置，用于满足相关接口 IP 白名单场景下的固定出口需求。
- REST API 请求复用统一配置的 `httpx.AsyncClient`，统一代理、超时和连接池边界；公开 API 直接使用业务名称并通过 `await` 调用，以 `aclose()` 管理生命周期。
- `CustomerContactDirectory` 接收 `qps` 配置，默认值为 50。限流位于 HTTP transport 边界，以平滑间隔约束单个 client 实例的真实出站请求；token 获取、业务请求及每次重试共享同一配额。
- `CustomerContactDirectory` 接收 `request_concurrency` 配置，默认值为 8，用于限制同时在途的 REST API 请求。QPS 与并发上限分别约束请求发起速率和在途数量。
- 企业内部自建应用鉴权由独立的异步 `httpx.Auth` 实现负责，只处理访问令牌获取、进程内缓存、并发刷新、请求注入和主动失效；token 不写入数据库。token 失效后的业务请求重放、可重试 HTTP 状态和传输故障重试统一由 `WeComCustomerClient` 负责。
- Pydantic 用于初始化配置、企业微信响应结构和公开只读数据对象校验；校验失败在网络边界转换为不泄露响应敏感内容的稳定异常。
- 代理地址可能包含认证信息，必须按敏感配置处理，不得出现在日志或异常文本中。
- `WeComArchive` 不提供 HTTP 服务，也不使用 httpx；会话拉取、解密和附件下载均通过企业微信会话存档 SDK 适配层完成。
- 会话存档 SDK 自身的网络要求和可配置能力必须依据官方文档或技术验证确定，不与 `CustomerContactDirectory` 的 HTTP 代理配置混用。

### 附件存储

- 附件二进制内容通过可插拔存储后端保存，不与关系数据库实现绑定。
- 关系数据库保存附件与消息的关联、原始文件名、媒体类型、大小、校验值、存储后端和对象键等元数据。
- 存储后端至少需要定义保存、读取和删除能力，并返回稳定的存储引用。
- `WeComArchive` 初始化时接收可选的 `attachment_storage`；未提供时使用内置本地文件存储。
- 自定义存储对象可以对接第三方存储服务；`run_forever()` 启动后不得切换当前后端。
- 首版只内置本地文件存储，不内置 S3 或其他第三方对象存储适配器；用户可以基于公开协议自行扩展。
- 附件写入与数据库事务之间的一致性策略仍待确定。

## 模块职责

1. 配置与密钥加载
2. 企业微信客户与客户群 API 适配
3. 企业微信会话存档 SDK 适配
4. 增量同步与游标管理
5. 消息解密、解析与附件下载
6. 原始消息和附件持久化
7. 企业微信官方消息结构映射与只读封装
8. 可配置的消息处理管线
9. 数据存储或下游投递
10. 重试、幂等与故障恢复
11. 日志、监控指标与审计

## 数据流

### 客户联系资料同步

外部调度器调用 `CustomerContactDirectory` → 分别执行客户资料与客户群资料同步 → 持久化客户、群、群成员关系及各自同步状态。

首版客户同步流程为：获取配置了客户联系功能的成员列表 → 由资料目录将成员按接口上限分组并在可配置并发上限内创建任务 → HTTP 客户端在每个分组内按游标顺序获取客户详情并按页返回 → 每页客户及跟进关系通过单写入锁顺序批量写入数据库。完整扫描成功后才更新未见记录状态；同一实例不允许同时执行两轮客户同步。

首版客户群同步流程为：通过游标获取客户群列表 → 逐个获取客户群详情 → 持久化群、成员和管理员关系。

首版采用可重复执行的全量快照同步，不依赖回调事件提供增量正确性。每次同步使用独立运行标识标记本轮所见数据；只有所有分页和详情请求均成功后，才将本轮未见的旧记录标记为非活跃。非活跃仅表示在一次完整、授权范围内的扫描中未再次出现，不等同于确认数据已被企业微信删除。

### 已知性能与异步边界

- 客户群列表、群详情以及群关系写入仍按顺序执行，尚未接入客户同步已经采用的有限并发、背压和批量事务模式。
- `sync_all_once()` 当前串行调用两个领域同步入口；它们会分别请求成员列表。近期先复用成员列表，再根据默认 SQLite 的写锁表现决定是否并行两个领域，不能仅用 `asyncio.gather()` 改变失败和事务语义。
- Alembic 通过 SQLAlchemy `run_sync()` 调用同步迁移入口。异步驱动可以适配其中的数据库 I/O，但同步迁移控制逻辑仍在事件循环线程执行，首次初始化期间可能造成停顿。
- 默认数据目录解析和目录创建发生在普通构造函数内，仍是同步文件系统操作。
- HTTP 响应完成后的 JSON 解析、Pydantic 校验，以及仓储层模型序列化、深拷贝和结果对象构造都是事件循环线程上的同步 CPU 工作。是否卸载线程应以真实数据下的事件循环延迟为依据，避免为小对象增加无效切换成本。
- `aiosqlite` 通过工作线程包装同步 SQLite；这能避免在事件循环线程直接执行 SQLite 调用，但数据库本身仍是单文件同步引擎，默认策略继续使用顺序批量写入。

### 会话存档同步

上层程序启动 `WeComArchive` 长期运行方法 → asyncio 调度器按配置间隔轮询会话存档 SDK → 解密与附件下载 → 原始数据持久化 → 更新同步检查点 → 调度用户消息处理函数 → 等待下一轮。

项目内部负责固定间隔轮询，但不负责 cron 等日历调度、进程守护或服务重启；这些由上层运行环境负责。

## 处理管线

- 原始消息可靠持久化后，才进入自定义处理器。
- 第一版处理器以用户注册的 Python 函数形式，在同一进程内按注册顺序调度。
- `async def` 处理函数作为协程运行；普通 `def` 处理函数提交到有并发上限的线程池，避免阻塞轮询调度器。
- 首版不提供多进程执行模式；当前预期处理器不包含 CPU 密集型工作。
- 同步线程中的处理函数无法被安全强制终止；是否向处理函数传入取消上下文、超时仅告警还是采用其他语义，暂待确认。
- 每个处理函数接收一个只读的 `Message` 公共对象，不接收 ORM 实例或可变的原始字典。
- `Message` 不重新定义企业微信消息协议，而是对官方解密结果提供薄封装；字段名称、消息类型和类型专属载荷以企业微信官方文档为准。
- 完整的原始解密数据必须保留，以兼容尚未识别或官方后续新增的消息类型。
- 框架生成的附件存储引用、处理状态等元数据与官方消息载荷分开保存，避免污染官方字段。
- 处理函数是相互独立的事件监听器：每个函数都收到同一个 `Message`，返回值被忽略，不会转换后续函数的输入或阻止其他函数执行。
- 同一条消息的多个处理器严格按注册顺序执行；不同消息可以并行处理。
- 处理消息的全局并发上限在初始化时配置，默认值为四。
- 需要过滤消息时，处理函数自行判断并直接返回。
- 处理器可以过滤、转换或消费消息，并应有清晰的输入输出协议。
- 单个处理器失败不得导致原始消息丢失或同步检查点回退不明。
- 每条消息与每个处理器的执行状态独立持久化，至少包含稳定处理器名称、状态、尝试次数和脱敏后的错误摘要。
- 单个处理器失败后继续执行后续处理器，并在之后的轮询周期中进行带退避的重试。
- 默认最多自动尝试三次；超过后标记为最终失败，等待用户显式重试或处理。
- 处理器应按幂等方式实现，因为进程中断可能导致至少一次执行语义下的重复调用。
- 每轮轮询记录包含消息数、处理成功数和失败数等信息的执行摘要。
- 处理任务通过数据库状态与轮询解耦；线程池或协程容量耗尽时，新任务保留为待处理状态，不得无限制占用内存。
- 首版使用数据库租约队列，不依赖 Redis、RabbitMQ 或外部任务框架。
- 消息、对应处理任务和同步检查点应在同一数据库事务中安全提交。
- 工作器领取任务时写入租约所有者和到期时间；进程异常退出后，到期任务可以被重新领取。
- `(message_id, handler_name)` 应具有唯一约束，避免为同一处理器重复创建消息任务。
- 任务至少包含待处理、执行中、成功、待重试和最终失败状态，并为领取、到期和重试查询建立索引。
- 正式的第三方插件发现、安装和隔离机制推迟到扩展需求稳定后设计。
- 官方消息类型清单和字段映射需要在实现前逐项查阅官方文档并形成测试样例。

## 设计关注点

- 只有相关数据得到安全处理后，才能推进同步检查点。
- 重复处理不能产生非预期的重复数据。
- 未识别的消息类型应当保留或进入隔离流程，不能被静默丢弃。
- 敏感配置和解密后的会话内容必须得到明确保护。
- `CustomerContactDirectory` 的代理地址及其中可能包含的用户名、密码属于敏感配置。
- SDK 集成边界应隔离原生 SDK 细节与应用业务逻辑。
- 客户联系资料同步失败或资料暂缺时，会话归档仍须保存原始标识并继续运行；不得将资料完整性作为消息持久化的前置条件。
- 同步状态应作为独立、可持久化和可检查的数据管理。
- 进程重启或消息重复拉取时，系统应保持幂等并可从检查点恢复。
- 长期轮询需要支持优雅停止、临时网络错误退避和不可恢复配置错误的明确退出行为。
- `stop()` 只发出停止请求；当前消息完成持久化和本轮处理器调用后，`run_forever()` 退出且不再开始下一轮轮询，随后释放资源。
