## D-004：原始消息先持久化，再运行处理管线

- 状态：已接受
- 日期：2026-08-30
- 决策：会话消息完成解密和必要的附件下载后，先可靠持久化原始数据并安全推进同步检查点，再交给可配置的处理器管线。
- 背景：自定义处理器不受核心同步逻辑完全控制，可能失败、超时或包含业务过滤规则。
- 影响：处理器故障不得造成原始消息丢失；消息处理状态需要与同步状态分开管理，并支持重试。

## D-009：使用 SQLAlchemy 和 Alembic 支持多种关系数据库

- 影响：模型、查询、迁移和测试需要保持跨数据库兼容；必须定义默认 SQLite 文件位置、初始化策略，并针对三种数据库建立兼容性测试。数据库驱动应按对应后端作为可选依赖安装。

## D-010：会话存档与客户群同步分离

- 状态：已取代，由 D-027 取代
- 日期：2026-08-30
- 决策：`WeComArchive` 只负责会话存档同步、默认持久化和消息处理；客户群列表及详情同步作为独立公开模块提供，不挂载到 `WeComArchive`。
- 背景：客户群资料同步与会话消息存档具有不同的业务职责和调用频率，不应混合在同一个类中。
- 影响：两个模块可以共享配置、网络和存储基础设施，但需要分别定义公开入口和验收标准。

## D-011：通过注册方法添加消息处理函数

- 状态：已接受
- 日期：2026-08-30
- 决策：`WeComArchive` 初始化后，用户通过 `register_handler` 注册消息处理函数。该方法可以多次调用，多个处理函数按注册顺序执行。
- 背景：消息持久化是框架默认行为，自定义处理属于可选扩展，并需要支持多个独立处理逻辑。
- 影响：仍需定义处理函数签名和返回值语义。

## D-012：处理器失败隔离与有限重试

- 状态：已接受
- 日期：2026-08-30
- 决策：处理器按消息分别记录执行状态。单个处理器失败时记录错误和尝试次数，继续执行后续处理器，不回滚原始消息或同步检查点。失败项在后续轮询周期中带退避重试，默认最多自动尝试三次；超过后标记为最终失败，等待用户显式处理。
- 背景：自定义业务逻辑可能出现临时或永久故障，不能让它阻断企业微信消息的可靠归档。
- 影响：需要稳定的处理器标识、处理执行状态表、脱敏错误记录、重试调度和同步结果摘要。处理器采用至少一次执行语义，文档必须要求用户尽量保证幂等。

## D-013：处理函数接收只读消息对象

- 状态：已接受
- 日期：2026-08-30
- 决策：注册的处理函数接收一个只读的 `Message` 公共对象，不直接接收数据库 ORM 实例或可变的原始字典。
- 背景：公共处理接口需要跨数据库保持稳定，并防止用户代码意外修改已归档的原始消息。
- 影响：需要定义稳定的 `Message` 数据契约和消息类型扩展方式；ORM 模型保持为内部实现。

## D-014：处理函数采用独立事件监听语义

- 状态：已接受
- 日期：2026-08-30
- 决策：所有已注册处理函数都接收同一个只读 `Message`，其返回值被忽略。处理函数不转换后续函数的输入，也不能阻止其他函数执行；需要过滤时由函数内部判断并直接返回。
- 背景：首版的自定义处理目标是响应已归档消息，而不是构建相互依赖的数据转换链。
- 影响：监听器之间保持低耦合，失败隔离和单独重试更清晰；若未来需要转换管线，应作为不同的扩展接口设计。

## D-015：会话存档采用长期轮询运行模型

- 状态：已接受
- 日期：2026-08-30
- 决策：用户初始化 `WeComArchive` 并注册处理函数后，调用长期运行方法。该方法按照初始化时配置的轮询间隔持续获取和处理最新消息，直到收到停止请求或发生不可恢复错误。
- 背景：会话存档需要持续接收新消息，而不是依赖上层调度器反复创建对象并触发单次同步。
- 影响：包内部负责固定间隔轮询和临时错误退避；外部运行环境负责进程启动、守护和重启。默认轮询间隔和停止时的安全处理边界仍需确定。

## D-016：使用 run_forever 和 stop 控制运行生命周期

- 状态：已接受
- 日期：2026-08-30
- 决策：`WeComArchive.run_forever()` 是阻塞式长期运行入口，`WeComArchive.stop()` 用于从程序内请求优雅停止。停止后应释放数据库连接和会话存档 SDK 等资源。
- 背景：持续轮询既需要简单的启动方式，也需要允许上层程序安全终止，而不能依赖强制杀死进程。
- 影响：`stop()` 需要能够安全地从其他执行上下文调用；它只设置停止请求，当前消息完成持久化和本轮处理器调用后退出，不再开始下一轮轮询，然后释放资源。

## D-017：使用 asyncio 与受限线程池执行处理器

- 状态：已接受
- 日期：2026-08-30
- 决策：`run_forever()` 内部使用 asyncio 协调轮询和处理任务。异步处理函数作为协程执行，普通同步处理函数提交到有并发上限的线程池。首版不支持多进程处理器。
- 背景：处理器预期以 I/O 操作为主，需要同时兼容同步和异步函数，并避免同步函数阻塞消息拉取与持久化；当前没有 CPU 密集型处理需求。
- 影响：处理任务状态需要持久化并与轮询解耦；需要定义线程与协程并发上限、积压和背压策略。卡死的同步线程无法被 Python 安全强制终止，但不应阻塞轮询主循环。

## D-018：使用数据库租约队列持久化处理任务

- 状态：已接受
- 日期：2026-08-30
- 决策：首版使用关系数据库中的任务表实现租约队列，不引入 Redis、RabbitMQ、Celery 等额外基础设施。消息、处理任务和同步检查点安全持久化；工作器通过有到期时间的租约领取任务，异常中断后允许其他工作器重新领取。
- 背景：项目需要处理任务可恢复，同时保持 Python 包安装即用和默认 SQLite 的体验。
- 影响：需要任务状态机、原子领取、租约续期与回收、唯一约束、退避、索引和积压指标，并分别验证 SQLite、MySQL 与 PostgreSQL 的并发语义。未来需要多主机大规模消费时，可以再增加可选外部消息代理后端。

## D-019：处理器使用稳定且唯一的名称

- 状态：已接受
- 日期：2026-08-30
- 决策：`register_handler` 接收可选的 `name`。未传入时使用处理函数的模块名和限定名生成；同一个 `WeComArchive` 实例中名称必须唯一，重复名称在 `run_forever()` 启动前报配置错误。
- 背景：处理任务、执行结果和重试状态需要在数据库中稳定关联到具体处理器，并在进程重启后保持可识别。
- 影响：lambda、局部函数或重命名函数可能产生不稳定的自动名称，文档应建议生产环境显式指定名称；处理器名称变更的任务迁移策略仍需设计。

## D-020：按消息并行、按处理器顺序执行

- 状态：已接受
- 日期：2026-08-30
- 决策：同一条消息的多个处理器严格按注册顺序执行，不同消息允许并行处理。消息处理并发上限作为初始化配置，默认值为四。
- 背景：单条消息的处理行为需要可预测，同时慢消息不应阻塞所有其他消息。
- 影响：调度器需要按消息维持顺序，并限制同时处于处理阶段的消息数量；实际默认值需要在 SQLite、MySQL 和 PostgreSQL 上进行负载验证。

## D-021：消息结构以企业微信官方定义为准

- 状态：已接受
- 日期：2026-08-30
- 决策：项目不重新设计消息字段和消息类型。`Message` 是企业微信官方解密消息结构的只读薄封装，官方字段和类型专属载荷保持原有语义，并完整保留原始解密数据。框架自身元数据与官方载荷分开存储。
- 背景：企业微信已经定义会话存档的消息格式，自建标准化模型会增加信息丢失、字段漂移和新类型兼容风险。
- 影响：实现前必须依据官方文档逐类建立字段映射和测试样例；未知或新增类型不得丢弃，用户仍可通过原始载荷访问。

## D-022：附件使用可插拔存储后端

- 状态：已接受
- 日期：2026-08-30
- 决策：附件二进制内容通过独立、可插拔的存储后端保存；关系数据库只保存附件元数据、消息关联和稳定存储引用。
- 背景：本地试用、单机部署和生产对象存储对附件保存方式有不同需求，不应将框架绑定到数据库二进制字段或特定云服务。
- 影响：需要稳定的附件存储协议、默认实现、幂等对象键、校验和删除语义，并处理文件写入成功但数据库事务失败等一致性问题。

## D-023：默认本地存储并在初始化时允许替换

- 状态：已接受
- 日期：2026-08-30
- 决策：未配置 `attachment_storage` 时使用内置本地文件存储；用户可以在初始化 `WeComArchive` 时传入实现存储协议的对象以对接第三方存储服务。`run_forever()` 启动后不允许切换存储后端。
- 背景：默认行为需要开箱即用，同时生产环境可能使用对象存储或企业内部文件服务。
- 影响：需要确定默认数据目录和公开存储协议；数据库中的每条附件记录必须包含后端标识和稳定对象键。首版只内置本地文件存储，不提供 S3 等第三方适配器，用户仍可自行实现存储协议。

## D-024：默认使用操作系统用户数据目录

- 状态：已接受
- 日期：2026-08-30
- 决策：`WeComArchive` 初始化时允许配置 `data_dir`；未配置时使用操作系统规范的用户数据目录。默认 SQLite 文件和本地附件分别保存到该目录下的独立子路径。
- 背景：安装目录可能只读，当前工作目录也可能随启动方式变化，不适合作为可靠的默认持久化位置。
- 影响：需要以跨平台方式解析用户数据目录，初始化时安全创建目录，并在日志和公开属性中明确实际使用位置。

## D-025：使用 Python 3.10 和 uv 管理项目

- 状态：已接受
- 日期：2026-08-31
- 决策：项目使用 Python 3.10 作为开发与运行版本，并使用 uv 管理虚拟环境、项目依赖和锁定文件。
- 背景：需要统一开发环境与依赖解析方式，减少不同开发和部署环境之间的版本偏差。
- 影响：项目元数据需要声明 Python 3.10 版本约束；依赖变更通过 uv 完成并提交锁定文件；测试和发布流程以 Python 3.10 为基准。

## D-026：使用 httpx 作为 HTTP 客户端

- 状态：已取代，由 D-028 取代
- 日期：2026-08-31
- 决策：项目可控范围内的 REST API、媒体下载及其他 HTTP 请求统一使用 httpx；异步数据流优先使用 `httpx.AsyncClient`。
- 背景：项目采用 asyncio 调度，并需要统一处理代理、超时、连接池和网络错误。
- 影响：网络适配层应集中创建和配置 httpx 客户端，不得让各模块自行绕过统一代理与安全配置；企业微信原生会话存档 SDK 的网络与代理能力仍需单独依据官方文档验证。

## D-027：客户联系资料目录与会话存档分离

- 状态：已接受
- 日期：2026-08-31
- 决策：以独立公共组件 `CustomerContactDirectory` 同步和查询客户、客户群及群成员资料；`WeComArchive` 只负责会话存档，不包含这些同步方法。资料目录内部拆分客户同步、客户群同步和资料仓储，并提供整体及分类单次同步入口。
- 背景：客户与客户群资料需要共同为会话提供联系人上下文，但它们不属于会话存档本身，调用凭据、更新频率和失败恢复方式也可能不同。
- 影响：两个组件同包交付并共享数据库基础设施，但分别维护凭据边界、网络接入、同步检查点与错误状态。会话消息始终保存原始 ID，不在归档链路中实时拉取客户资料；资料缺失或同步失败不得阻塞会话归档，查询和处理阶段通过本地资料目录关联当前资料。具体网络边界见 D-028。

## D-028：会话存档 SDK 与客户联系 HTTP 边界分离

- 状态：已接受
- 日期：2026-08-31
- 决策：`WeComArchive` 不提供 HTTP 服务，也不使用 httpx；会话拉取、解密和附件下载统一通过企业微信会话存档 SDK 适配层完成。只有 `CustomerContactDirectory` 调用客户和客户群 REST API 时使用 httpx，并在该组件边界内管理可选 HTTP 代理。
- 背景：会话存档和客户联系资料来自不同的企业微信接入机制，不能把 REST API 客户端或代理配置错误地视为 `WeComArchive` 的依赖。
- 影响：两个组件可以共享数据库，但不能共享 HTTP 客户端或混用网络配置。SDK 的网络能力依据其官方接口单独验证；客户联系 REST API 的超时、连接池、代理和错误映射由集中配置的 httpx 客户端负责。

## D-029：客户联系资料首版只支持企业内部自建应用

- 状态：已接受
- 日期：2026-08-31
- 决策：`CustomerContactDirectory` 首版只支持企业内部自建应用，以企业 `corp_id` 和“客户联系 Secret”获取访问令牌；第三方服务商授权模式不在首个交付里程碑范围内。
- 背景：内部自建应用与第三方应用的授权流程、权限边界和外部联系人标识语义不同。先限定单一接入模式，可以在不引入套件授权和多租户复杂度的情况下验证资料同步、持久化和恢复语义。
- 影响：首版配置和测试围绕单企业凭据设计，但网络客户端与同步服务仍保持边界清晰，未来增加第三方授权时可以替换令牌提供者，而不改动资料仓储接口。

## D-030：资料目录初始化时自动执行数据库迁移

- 状态：已接受，开发阶段范围由 D-034 限定
- 日期：2026-08-31
- 决策：`CustomerContactDirectory` 首次进入异步上下文或首次执行公开异步方法时，自动通过 Alembic 升级到包内当前 schema；默认 SQLite 和显式配置的数据库采用相同迁移路径。
- 背景：首版不提供 CLI，并要求 Python 包开箱即用。如果要求调用方在创建资料目录前另行执行迁移，将产生一个未暴露的部署步骤。
- 影响：数据库账号必须具备执行当前迁移所需的 DDL 权限；迁移失败时首次异步初始化立即失败，不启动资料同步。未来如生产部署需要迁移审批，可以增加仅检查版本或显式迁移入口。

## D-031：客户联系鉴权使用独立的 httpx Auth

- 状态：已取代，由 D-032 取代
- 日期：2026-08-31
- 决策：客户联系 REST API 的内部自建应用鉴权封装为独立的 `httpx.Auth` 实现，同时提供同步与异步认证流，负责访问令牌获取、提前过期缓存、并发刷新，以及令牌无效或过期后的单次刷新重试。`WeComCustomerClient` 同时提供基于 `httpx.Client` 的同步方法和基于 `httpx.AsyncClient` 的 `async_*` 方法，只负责业务 API 调用和最终响应的错误映射。
- 背景：鉴权生命周期与客户、客户群业务请求无关，并且未来增加其他授权模式时需要能够替换令牌提供者，而不改动资料同步逻辑。
- 影响：鉴权实现必须使用 HTTPX 认证流发起令牌请求和重放业务请求，继续保证 Secret、访问令牌及代理认证信息不会进入公开异常；同步和异步客户端分别维护令牌缓存与并发锁，异步客户端按需创建并通过 `aclose()` 释放。

## D-032：客户联系链路统一异步并划分校验、鉴权和重试职责

- 状态：已接受
- 日期：2026-08-31
- 决策：`CustomerContactDirectory` 的 HTTP 请求、数据库迁移与数据库会话统一采用异步模式；配置、企业微信响应和公开数据对象使用 Pydantic 校验。自定义 `httpx.Auth` 只负责 token 获取、进程内缓存、并发刷新、注入和失效，不把 token 持久化到数据库；token 失效后的请求重放、临时 HTTP 状态和传输故障重试由 `WeComCustomerClient` 集中处理。
- 背景：同步/异步双栈增加重复实现和生命周期复杂度；鉴权类承担业务请求重试会模糊职责；未经结构校验的字典直接进入仓储层会延迟暴露上游协议变化。
- 影响：资料目录公共 I/O 方法均需 `await`，资源通过异步上下文或 `aclose()` 释放；默认 SQLite 使用 `aiosqlite`，MySQL 和 PostgreSQL 使用可选的异步驱动。同步调用方需要迁移到 asyncio；重试参数和错误映射由 client 统一维护。

## D-033：客户联系 HTTP 请求默认限制为 50 QPS

- 状态：已接受
- 日期：2026-08-31
- 决策：`CustomerContactDirectory` 和内部 `WeComCustomerClient` 接收正数 `qps` 配置，默认值为 50。限流器位于 HTTPX 异步 transport 边界，按平滑间隔限制单个 client 实例的真实出站请求；token 获取、业务请求及每次重试共享同一 QPS 配额。
- 背景：分页同步和故障重试可能在短时间产生密集请求，需要提供稳定且可配置的客户端侧速率控制。只在业务方法入口限流会漏计鉴权请求，并可能让重试绕过配额。
- 影响：默认情况下相邻出站请求至少间隔约 20 毫秒。多个 client 实例各自维护配额，不构成跨进程或跨实例的全局限流；如未来需要全局配额，应引入可共享的限流后端。

## D-034：开发阶段暂不维护数据库历史迁移兼容性

- 状态：已接受
- 日期：2026-08-31
- 决策：项目 schema 尚未稳定时，不投入历史版本升级路径、回滚脚本和跨版本迁移测试。现有 Alembic 初始化流程暂时保留，用于让新数据库达到当前 schema；后续不兼容的 schema 变更可以要求重建开发数据库。
- 背景：当前重点是验证客户联系与会话存档的功能边界，开发数据库不承载必须保留的生产数据。此时持续维护每个临时 schema 之间的升级路径会增加成本，并过早固化数据模型。
- 影响：近期数据库验证只覆盖当前 schema 在受支持数据库上的初始化和基本读写，不承诺旧开发数据库原地升级。任何需要保留的数据应先导出或备份；进入稳定发布、接入真实需保留数据或明确生产部署前，必须重新制定版本化迁移、备份、回滚与发布策略。

## D-035：客户分组有限并发抓取并批量写入数据库

- 状态：已接受
- 日期：2026-09-01
- 决策：资料目录按企业微信接口允许的成员数量分组，并在 `request_concurrency` 上限内为不同分组创建抓取任务；HTTP 客户端只负责在一个合法分组内按游标顺序翻页，并在每次请求后按页返回数据。每页数据通过单写入锁，在一个数据库事务内顺序更新客户及跟进关系；同一资料目录实例不允许同时执行两轮客户同步。
- 背景：原实现对所有成员分组和每条客户记录完全串行，网络等待无法重叠，且每条记录单独开启事务。仅提高 HTTP 并发而同时并发写 SQLite 会引入锁竞争，也可能让同一客户的多条跟进关系发生插入竞争。
- 影响：`CustomerContactDirectory` 和内部客户端新增默认值为 8 的 `request_concurrency`；资料目录用它限制活跃分组任务，客户端用它兜底限制同时在途的真实请求。QPS 继续限制请求发起速率。任一抓取或写入失败时会取消其余分组任务，且不执行完整扫描的最终状态更新；MySQL 和 PostgreSQL 暂时采用与 SQLite 相同的顺序批量写入策略。
