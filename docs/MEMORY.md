# 项目记忆

## 长期背景

- GitHub 仓库已经创建并克隆到本地。
- 本项目用于实现企业微信会话内容存档集成。
- 已确定使用 Python 作为开发语言。
- 用户希望先制定计划并建立项目记忆，再开始编写业务代码。

## 当前状态

- 已初始化仓库协作约定、计划、架构、决策和项目记忆文档。
- 已明确三个功能阶段：客户群与成员同步、会话存档及附件同步、可配置的消息处理管线。
- 最终以可安装、开箱即用的 Python 包交付，并允许其他 Python 程序集成。
- 首版不提供命令行工具；`WeComArchive` 是会话存档主类，客户群列表与详情同步通过独立公开模块提供。
- 主入口类初始化时必须传入企业微信会话存档凭据；数据库和 HTTP 代理配置可选。
- 持久化层统一使用 SQLAlchemy 2.x ORM 和 Alembic，首版支持 SQLite、MySQL 和 PostgreSQL；未配置数据库时自动使用 SQLite，但不绕过 ORM。
- `WeComArchive` 采用长期运行模型，在初始化和注册处理器后按配置间隔持续轮询新消息；外部系统只负责启动、守护和重启进程。
- 长期运行入口为阻塞式 `run_forever()`，程序内可调用 `stop()` 请求优雅退出并释放资源。
- 优雅停止会等待当前消息完成持久化和本轮处理器调用，不再开始下一轮轮询。
- 已确定原始消息先持久化，再运行第一版进程内处理器；正式插件机制后续按需演进。
- 用户通过可重复调用的 `register_handler` 注册多个消息处理函数，处理函数按注册顺序执行。
- 处理器名称可显式指定，默认由函数模块名和限定名生成；名称必须唯一，冲突在运行前报错。
- 同一消息的处理器按注册顺序执行，不同消息可并行，默认最多并行处理四条消息并允许初始化时配置。
- 每个处理函数接收只读 `Message`，它薄封装企业微信官方消息结构并完整保留原始解密数据，不另建自定义消息协议。
- 处理函数采用独立事件监听语义：接收同一消息、返回值忽略，函数内部自行过滤，不影响其他监听器。
- 处理器失败相互隔离，不回滚消息或游标；失败项跨同步调用退避重试，默认最多三次，之后进入等待人工处理的最终失败状态。
- `run_forever()` 内部使用 asyncio 调度；异步处理函数作为协程运行，同步处理函数进入受限线程池，首版不支持多进程处理器。
- 同步处理函数的超时与取消语义暂缓决定；线程无法被安全强制终止，是否增加取消上下文仍待确认。
- 首版以数据库租约队列持久化处理任务，不依赖外部消息代理；任务支持原子领取、租约到期恢复、唯一约束和状态重试。
- 附件二进制内容使用可插拔存储后端，关系数据库保存附件元数据和稳定存储引用；默认使用本地文件存储，可在初始化时传入第三方存储对象替换。
- 首版只内置本地文件存储，不内置第三方对象存储适配器。
- 尚未确定附件写入与数据库事务的一致性策略和部署方式。
- 当前没有业务代码。
